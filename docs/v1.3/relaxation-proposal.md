# 硬条件放宽改造方案

Oct 24, 2026 · @jinlin yu

## 背景

现有降级只在 BM25 一路、只放宽必含食材，放宽进来的候选到资格检查时又按原始条件全部判 fail，用户最终看到的只是「没有推荐」。本方案把放宽改为在检索层统一决策：用一次聚合统计各放宽方案的命中数，按代价最小的原则放宽必含食材或数值条件，两路一起重新检索，并把放宽后的结果作为「相似推荐」明确标出偏差。

**现有做法**

- BM25 严格结果少于 5 条时，按 original → any\_required → no\_required 逐层放宽必含食材；排除条件、数值条件、手动 Labels 全程保留。
- Vector 始终带着原始必含过滤，不放宽。
- 数值条件从不放宽。
- 必含食材默认是 OR，只有 AND 表达式才会触发 any\_required。

**实测问题**

| 用例 | 现象 |
| --- | --- |
| salad，必含 durian，排除 onion，热量 ≤ 300，Label vegan | original 0 条 → no\_required 补 860 条，全部不含 durian，资格检查时会全部判 fail；Vector 带 durian 过滤只找到 1 条 |
| fruit salad with durian | durian 全库只有 6 道（Durian Cake、Durian ice cream……），没有沙拉；去掉 durian 得到 7,067 道普通水果沙拉，失去了用户最在意的一点 |
| beef AND onion AND pineapple，≤ 15 分钟 | 严格 2 条；「三选二」680 条里有 674 条只是 beef + onion，pineapple 全丢；而时间放宽到 23 分钟有 12 条且保留全部食材 |

结论：召回数量只是决策依据，不是目标；放宽哪个条件、放宽多少，要按对用户意图的影响来选，并且要告诉用户放宽了什么。

## 设计原则与条件分级

**原则**

1. **在检索层决策，流程只走一遍**：可以放宽的条件（必含食材、数值条件）恰好都是 ES 层过滤的条件，检索层已有全部信息，不需要等资格检查后再回头检索。
2. **资格检查始终按原始条件**：放宽只改变找哪些候选；放宽候选标为 near\_miss 并记录偏差，不计入正式推荐。
3. **告诉用户放宽了什么**：完全符合的和放宽后的分两个区域展示，每张卡片标出具体差在哪里。
4. **两路一起放宽，查询文本不变**：Vector 带着放宽后的过滤、原始查询文本检索，会把「缺一个条件但最像」的食谱排在前面。

**条件分级**

| 条件 | 是否放宽 | 放宽方式 |
| --- | --- | --- |
| 数值条件（总时间、热量、蛋白质） | 自动 | +20% → +50% → 去掉；下限条件（如蛋白质 ≥ 30 g）往下调 |
| 非核心必含食材 | 自动 | 明确去掉某一个食材，不用「满足多数」 |
| 核心必含食材 | **不自动** | 一般只作为用户可点击的选项：去掉，或换成相近食材；例外见下方「唯一核心食材」 |
| 排除条件、手动 Labels | **不放宽** | 可能涉及过敏、忌口，或是用户亲手加的过滤 |
| Dish name、Dish type、菜系、餐次 | 不处理 | 召回本来就是加权；资格检查判得宽松，一般不是瓶颈 |

**核心食材**：满足任一条即为核心——出现在菜名或搜索目标里（"pineapple beef stir fry" 的 pineapple）；用户加了 must、especially 等强调；只有一个必含食材。用户写了 "X or Y" 时已经是 OR 条件，不算单一核心。核心标记由意图解析给出，后端按上述规则兜底计算。

**唯一核心食材**：召回过滤条件里只有这一个核心食材（没有其他必含食材、数值条件、手动 Labels；只看 ES 硬过滤条件，Dish name、Dish type 只参与文本匹配和加权，不计入；排除条件始终保留，也不影响判定）时，严格候选不足可以自动去掉它做召回。找回来的菜在资格检查中仍按原始条件判：缺少该食材记为 `near_miss`，偏差写「不含 X」，**不算合格、不计入正式推荐**。展示时先说明库里的实际情况（如「库里没有 durian 水果沙拉；有 6 道 durian 食谱」），严格召回的含 X 食谱仍按各自状态归入 not eligible / unconfirmed，不另建分组；提示语由后端在 relaxation 结果里给出（X 名称、严格命中数），前端只显示一句，再列「接近的选择」。

## 触发规则与流程

**严格候选** = BM25 严格检索结果 + Vector 结果（按 recipe\_id 去重）。按两路合计判断，不按单路：BM25 为 0、Vector 有结果时，Vector 的结果同样满足全部 ES 硬过滤，不需要放宽；单路放宽补进来的候选到资格检查时会全部判 fail。

| 情况 | 判断依据 | 处理 |
| --- | --- | --- |
| A. 严格候选充足 | 严格候选 ≥ K\_strict | 正常资格检查与生成，丢弃并行返回的放宽统计 |
| B. 严格候选不足 | 严格候选 < K\_strict | 选择放宽方案 → 两路放宽检索 → 与严格候选合并后做一次资格检查 |
| C. 严格候选充足但 pass = 0 | 资格检查后无合格 | 不重新检索。卡住的是类别排除、菜型等不可放宽的条件；从资格检查结果统计各条件失败次数，告诉用户「找到 N 道，但都不满足 X」 |

严格检索和放宽统计同时发出；严格候选充足就走左侧正常流程，不足时直接用已返回的统计结果选择放宽方案，端到端不增加等待。

## 放宽统计：一次聚合拿到所有方案的命中数

统计只看过滤条件、不带文本查询（数据口径），回答「放宽后库里有没有」。审计过的结构如下：

- **顶层 query**：排除条件、手动 Labels（不放宽），再加上所有食材方案共同的必含食材（至少包含核心食材），先缩小扫描范围。
- **`filters` 聚合**：每种食材方案一个桶——strict（原始必含表达式），以及每个非核心食材各去掉一个（drop\_onion、drop\_beef……）。
- **`range` 子聚合**：每个数值条件一层，档位为原值、×1.2、×1.5。上限用 `to`、下限用 `from`；区间可以重叠，结果直接是累计数。「去掉该条件」取上一层的 doc\_count。
- **`missing` 聚合**：统计缺少数值字段的食谱，提示里说明这部分放宽也救不回。

```json
GET recipes_clean/_search
{
  "size": 0,
  "timeout": "800ms",
  "query": {"bool": {
    "filter": [ { "terms": { "ingredients": ["beef", "ground beef"] } } ],
    "must_not": [ /* 排除条件 */ ]
  }},
  "aggs": {
    "ingredient_variants": {
      "filters": { "filters": {
        "strict":         { /* beef AND onion AND pineapple */ },
        "drop_onion":     { /* beef AND pineapple */ },
        "drop_pineapple": { /* beef AND onion（pineapple 为核心时不生成） */ }
      }},
      "aggs": {
        "time": {
          "range": { "field": "total_time_minutes",
                     "ranges": [ {"key": "t<=15", "to": 15.01}, {"key": "t<=18", "to": 18.01}, {"key": "t<=23", "to": 23.01} ] },
          "aggs": { "calories": { "range": { "field": "calories",
                     "ranges": [ {"key": "c<=500", "to": 500.01}, {"key": "c<=600", "to": 600.01}, {"key": "c<=750", "to": 750.01} ] } } }
        }
      }
    },
    "time_missing": { "missing": { "field": "total_time_minutes" } }
  }
}
```

**耗时**（Kibana 实测）：典型情况（3 种食材方案 × 时间 3 档 × 蛋白质 3 档，带排除条件，未加顶层食材过滤）289 ms；全库最坏情况 444 ms。加上顶层共同食材过滤后预计更低。

**接入方式**：与严格检索并行发出（严格检索每路 4～5 秒，完全覆盖）；开启 request cache；超时后退回兜底——Vector 带最宽松的可放宽条件检索，按偏差大小排序。

## 选择放宽方案

| 级别 | 动作 | 执行方式 |
| --- | --- | --- |
| 1 | 数值条件 +20% | 自动 |
| 2 | 去掉一个非核心必含食材 | 自动 |
| 3 | 数值条件 +50% | 自动 |
| 4 | 去掉数值条件 | 自动，写明「已去掉 ×× 限制」 |
| — | 去掉或替换核心必含食材 | 永不自动，只作为按钮 |

**规则**

1. **只考虑瓶颈**：放宽后命中数没有增加的动作跳过。
2. **先单后双**：先试只放宽一个条件，按级别从低到高，第一个命中数 ≥ K\_relaxed 的即采用；都不够，再试两个条件的组合（按两个级别之和排序），最多两个。
3. **同级比较**：选放宽比例之和更小的；去掉非核心食材有多个可选时，选命中数刚好够用的那个。
4. **明确指定去掉哪个食材**，不用「满足多数」：「三选二」的结果会被最常见的组合淹没。
5. **用户偏好覆盖**（可选）：解析到 "time is flexible" 就把数值动作提前，"must have all" 就把食材动作后移。
6. **没有可行方案**：自动动作用完仍不够，说明卡住的是核心食材或不可放宽的条件，进入「没有符合的食谱」展示。

**示例：beef AND onion AND pineapple，总时间 ≤ 15 分钟**（实测命中数）

| 方案 | 命中数 |
| --- | --- |
| 原始条件 | 2 |
| 时间 ≤ 18 分钟（+20%） | 2 |
| 时间 ≤ 23 分钟（+50%） | 12 |
| 去掉 onion | 7 |
| 去掉 beef | 3 |
| 去掉 pineapple | 674 |
| 去掉 onion + 时间 +50% | 24 |

| 用户表达 | 核心食材 | 选择过程 | 结果 |
| --- | --- | --- | --- |
| "beef and onion with pineapple, under 15 minutes" | 无 | 级别 1 无增加；级别 2 中去掉 onion（7）、beef（3）不够，去掉 pineapple（674）够了 | 放宽「必含 pineapple」，卡片标「缺少 pineapple」 |
| "pineapple beef stir fry with onion, under 15 minutes" | pineapple | 级别 1 无增加；级别 2 只能去掉 onion（7），不够；级别 3 时间 ≤ 23 分钟（12）够了 | 保留全部食材，只放宽时间；卡片标「20 分钟，超出 5 分钟」 |

同样的条件组合，用户表达不同，系统选择不同的放宽方式，且都能讲清理由。

## 放宽检索、资格检查与展示

### 放宽检索

- 选定方案后，BM25 与 Vector **两路都用放宽后的 filter 再检索一次**；查询文本（BM25 关键词、Vector 主体与范围文本）保持不变，只改 filter。
- 每路取 K\_relaxed 条，与严格候选按 ID 去重；**严格候选整体排在前面**，放宽候选在后，合计截断到 Top 100。
- 放宽检索可与严格检索并行发起（统计聚合在严格检索返回前就能算完时），否则在聚合结果出来后串行补一次。
- 每条候选携带：
  - `source_level`: `strict` | `relaxed`
  - `relaxation`: 本次放宽的条件列表，如 `[{"type":"numeric","field":"minutes","from":18,"to":23}, {"type":"drop_ingredient","value":"onion"}]`

### 资格检查

- 资格检查**始终按用户原始条件**判定，不按放宽后的条件。
- 严格候选：沿用 pass / fail / unknown / not\_checked。
- 放宽候选：只违反被放宽的条件、其余硬条件全部 pass → `near_miss`，并记录 `deviations`（如「用时 22 分钟，超出 18 分钟上限 4 分钟」「不含 onion」）；违反其他硬条件 → fail。例外：放宽候选的 Dish name 为 unknown（边界菜，如甜品型沙拉、水果为主的凝胶沙拉）时也记为 near\_miss，偏差追加「菜型不完全一致」；只有明确是另一种菜（如 Durian Cake）才判 not\_matched → fail。严格候选的 Dish name unknown 仍按原规则进 unconfirmed。
- 停止规则：pass 达到目标数即停；未达到时继续检查，直到凑满 5 条 `near_miss` 或 Top 100 用完。
- `near_miss` 不计入正式推荐数量。

### 展示

| 情况 | 展示 |
| --- | --- |
| pass ≥ 目标数 | 只展示正式推荐，不提放宽 |
| pass 较少，有 near\_miss | 先展示 pass；下方单独一栏「接近的选择」，每条标出偏差 |
| pass = 0，有 near\_miss | 说明没有完全满足的食谱，列出 near\_miss 与各自偏差 |
| 无可行放宽方案（只剩核心食材放不了） | 告知库里的实际情况，如「库里有 6 道 durian 食谱，没有 durian 水果沙拉」，给出保留核心食材的备选，并提供「去掉 durian」「换成其他水果」按钮 |
| 情况 C：严格候选多但 pass = 0 | 不重新检索；说明是哪类不可放宽条件（排除、Labels 等）导致不通过 |

- 总结模型的 prompt 分两组传入：正式推荐（pass）与接近的选择（near\_miss + deviations），并附 `relaxation`，要求模型明确区分两组、不把 near\_miss 说成符合要求。

## 多方案放宽（v2）

### 背景

现有设计只选一个代价最低的放宽方案，找到足够结果就停止。导师（Fenner）的建议：系统无法知道用户更看重哪个条件，A AND B 完整匹配为 0 时，应同时提供「满足 A、不满足 B」和「满足 B、不满足 A」两组结果；A AND B AND C AND D 时，ABC、ABD、ACD、BCD 都可能有价值。目标是在不推翻现有框架的前提下，让放宽结果兼顾多样性，并清楚说明每组偏离了哪些要求。

现有框架里能直接复用的：放宽统计聚合一次就算出了所有方案的命中数；代价定义；资格检查始终按原始条件判定；接近的选择（near\_miss）的判定逻辑。

### 方案选择规则

1. **候选**：放宽统计里命中数 ≥ 3 的方案（原门槛 10；多组一起展示，单组不需要那么多）。
2. **排序**：先按放宽了几个条件（1 个优先），再按代价从低到高；代价相同时选命中数刚好够用的。
3. **贪心挑选**，同时满足两条才选：
   - 不能放宽已选方案放宽过的条件（时间 ×1.2 与 ×1.5 只保留代价低的）；
   - 不能是已选方案的超集（已选「去掉 A」，跳过「去掉 A + 放宽时间」）。
4. **最多 3 个**。可行的单条件方案不足 2 个时，才从同时放宽 2 个条件的方案里补，同样满足上面两条。
5. **一个都没有**：卡住的是核心食材或不可放宽的条件，走现有「没有可行方案」提示，不再检索。

核心食材、排除条件（过敏、忌口）、必含类别、OR 组合、手动 Labels 仍然不放宽，与 v1 一致。

**示例**：beef ∧ onion ∧ pineapple，时间 < 15 分钟，无核心食材。

| 方案 | 命中数 | 代价 | 结果 |
| --- | --- | --- | --- |
| 时间 → < 18 | 2 | 1 | 不足 3，不可行 |
| 去掉 onion | 2 | 2 | 不足 3，不可行 |
| 去掉 beef | 124 | 2 | 选中：第 1 组 |
| 去掉 pineapple | 244 | 2 | 选中：第 2 组 |
| 时间 → < 23 | 11 | 3 | 选中：第 3 组（放宽的是时间，不重复） |
| 去掉时间限制 | 127 | 4 | 跳过：与第 3 组同为放宽时间 |
| 去掉 beef + 时间 < 18 | 253 | 3 | 跳过：第 1 组的超集 |

最终 3 组：缺 beef、缺 pineapple、时间略超。v1 只会给出「去掉 beef」一组。

### 召回执行

| 查询 | 做法 | 请求数 |
| --- | --- | --- |
| 严格 BM25 + 严格 Vector | 不变，每路最多 500 条 | 2 |
| 放宽统计 | 不变，一次聚合算出所有方案命中数 | 1 |
| 放宽 BM25 | 每个选中方案一个子查询，打包进一个 `_msearch`；查询文本相同，只换过滤条件；每个方案 5 条，按顺序返回 3 个结果列表 | 1 |
| 放宽 Vector | 只查一次，过滤条件为「方案 1 OR 方案 2 OR 方案 3」，k = 15，num\_candidates = 100 | 1 |
| 补查 kNN | 只有某组凑不够配额时，才为该组单独补一次 | 0–2，通常为 0 |

- 查询向量复用严格召回那一次，不重新编码。
- 命中数 ≤ 20 的方案直接用过滤条件取回全部，不走 kNN。
- 不把所有方案合成一个 OR 查询的 BM25：排序只看相关度，某组可能占满前几名，另一组一条都没有，无法保证每组配额。

### 资格检查：接近的选择按偏差分组

- 判定仍按原始条件，near\_miss 的定义不变。
- 每条 near\_miss 增加 `group_key`，取值是**它实际不满足的条件集合**，而不是召回时用的方案（一道菜可能被几个方案同时召回）。例如 `missing:durian`、`numeric:total_time`；另记 `source_plans` 便于追溯。
- 同时不满足两个条件的单独成组，排在最后或不展示。
- 停止规则：由「near\_miss 凑够 5 条就停」改为「**每组凑够 2 条**，或该组候选已检查完」。合格满 20 条的停止条件不变。

### 生成与展示

- 接近的选择由一个扁平列表改为按组展示，每组 2–3 条，最多 3 组；组标题写「保留 X，未满足 Y」，卡片上保留偏差徽标。
- 组的排序：满足的原始条件多的在前 → 放宽代价小的在前 → 意图里识别出的用户强调或偏好。
- 总结模型拿到分组后的数据，每组写一句说明；正式推荐仍只来自合格（pass）的菜。
- 有合格但不足目标时：先展示合格，下方接分组的接近选择。
- 只有一组可行时（如 durian）：只展示这一组，并说明另一种放宽方式在库里没有结果。

### 性能风险与实验

- 只在严格候选不足 10 条时触发，常规查询不受影响。
- 放宽阶段通常仍是 2 个请求（1 个 `_msearch` + 1 次 kNN），与 v1 相同；主要风险是本地单节点 ES 并发 kNN 的 CPU 竞争拉长 p95。
- 实验：扩展 `scripts/benchmark_retrieval_depth.py`，用 20–30 条会触发放宽、带 2–4 个 AND 条件的查询，对比三种做法：单方案（v1）、多方案全部分开查、多方案 BM25 分开 + Vector 合并。
- 指标：
  - 多样性：展示的接近选择里有几种不同的「满足条件组合」；
  - 条件覆盖：每个原始条件在展示结果里至少被满足一次的比例；
  - 产出与成本：每组 near\_miss 数、模型调用次数、端到端 p50 / p95 延迟；
  - 主观评价：少量用户或 LLM-judge 判断哪种展示更有用。
- 消融：最多选几组（1 / 2 / 3）、每组配额（1 / 2 / 3）。
